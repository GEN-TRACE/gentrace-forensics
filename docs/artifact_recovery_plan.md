# 시나리오 PDF 기반 아티팩트 추출·복원 개선 계획

상태: 아래 내용은 설계 당시의 계획이다. 현재 구현 계약은 [artifact_outputs.md](artifact_outputs.md), 검증 현황과 미검증 범위는 [artifact_validation.md](artifact_validation.md)를 따른다.

검토 자료: `시나리오_분석__지민.pdf` 39쪽의 본문과 주요 증거 화면, 현재 `feat/pipeline-cli` 코드, DeepFake_DeepVoice E01 실행 결과. PDF는 관측 사례이며 모든 URL에 적용할 수 있는 일반 규칙으로 취급하지 않는다.

## 1. 목표와 완료 기준

조사자가 E01에서 확인할 수 있는 **업로드 관련 파일, 생성 결과, 관련 메타데이터, 네트워크 상태 흔적**을 근거와 함께 제시한다. 열 수 있는 파일은 실제 형식으로 내보내고, 파일 본문이 없거나 일부만 남은 경우에는 해당 상태를 명시한다.

완료 기준:

- 캐시 레코드 수와 고유 아티팩트 수, 복원된 파일 수를 각각 집계한다.
- 메타데이터 JSON 한 건에 파일 여러 개가 있으면 개별 아티팩트로 만들고 원래 JSON 위치와 연결한다.
- 한 파일의 여러 캐시 엔트리·미리보기·다운로드 변형은 관계를 유지하면서 묶는다.
- 파일 역할, 역할 판단 근거, 저장된 표현 형태, 복원 상태를 각각 기록한다.
- 파일 열기·재생 또는 문서 형식 검증을 수행하고, 검증되지 않은 항목을 완전 복원으로 표시하지 않는다.
- 모든 결과에서 이미지 → 프로필 → 원본 파일·오프셋 → 캐시 엔트리/JSON 필드 → 내보낸 파일을 역추적할 수 있다.
- 캐시에서 얻은 URL을 현재 서버에서 열어 확인하는 작업은 별도의 온라인 수집이다. 기본 실행은 로컬 증거만 분석하며 PDF에 있는 URL로 자동 접속하지 않는다.

### 관측과 추론을 구분할 부분

- PDF의 DeeVid·ChatGPT·ElevenLabs 일부 화면은 URL에 새로 접속해서 파일을 본 결과다. 해당 바이트가 원래 E01에 모두 존재한다는 증거로 사용하지 않는다.
- PDF의 Gemini 사례는 실제 이미지 대조를 포함한다. 크기나 URL 경로만 뽑아 자동 분류 규칙으로 일반화하지 않는다.
- PDF의 ElevenLabs `/samples/` 생성 결과 해석과 현 코드의 업로드 고정 해석 중 하나를 임의로 채택하지 않는다. 파일별 ID·응답·실제 재생 내용·원본 기록을 대조한다.
- PDF의 `.docx` 설명과 `.doc` 파일명, mp4 항목 설명과 JSON 화면 등 표기 차이는 원본 MIME·바이트·출처로 해소한다.
- 같은 네트워크 파티션 키만으로 동일 사용자 세션이나 특정 생성 행위를 확정하지 않는다. `expiration`과 `broken_until`은 만료·재시도 시각이며 방문/생성 시각으로 쓰지 않는다.
- PDF와 현재 E01의 식별자 일부는 연결되지만, 모든 사례가 동일한 수집본에 들어 있다고 전제하지 않는다. 문서상 날짜, 수집 시점, 캐시 시각, 서비스 생성 시각을 따로 기록한다.

## 3. 현재 확인한 실패 사례를 회귀 기준으로 고정

DeepFake_DeepVoice 실행의 2,285건은 캐시 레코드 수다.

- DeeVid 업로드 64건 중 61건은 `my-assets` 연결이 없고 3건만 연결됨. 미연결 61건을 사용자 업로드 확정으로 표시하면 실패.
- DeeVid 생성 44건은 Range 자식 25건, 본문 없는 HTTP 206 응답 13건, 커버 이미지 6건임. 이를 완전한 영상 44개로 집계하면 실패.
- ElevenLabs 업로드 5건은 JSON 메타데이터임. 복원한 오디오 5개로 집계하면 실패.
- 선택했던 `.bin`은 실제 WebP이며 URL 파일명은 `.jpg`임. 형식을 확인한 WebP 사본은 원본 본문과 동일한 해시여야 함.
- Gemini 17건은 JPEG/PNG 본문을 가진 레코드임. 변형과 동일 자산 관계를 확인하기 전 고유 생성물 17개라고 단정하면 실패.

574건·2,285건 파싱의 보존 여부는 회귀 지표다. 개선 후 최종 아티팩트 수가 이 숫자와 같을 필요는 없다.

## 4. 데이터 계약 제안

기존 `AcquiredCache → ClassifiedEntry → NormalizedArtifact` 출력은 진단·호환용으로 보존한다. 최종 아티팩트 계약을 별도로 설계해 캐시 엔트리와 파일 개체를 구분한다. 아래 필드는 초안이며 `schemas/` 구현 전에 획득·분류·정규화 담당자가 합의한다.

| 축 | 제안 필드/값 | 의미 |
|---|---|---|
| 개체 | `artifact_id`, 서비스 자산 ID, 프로필/케이스 ID | 같은 파일의 여러 관측·변형을 연결하는 식별자 |
| 역할 | `role`: upload / generated / unknown | 파일의 용도에 대한 판단 |
| 근거 | `attribution`: evidence_linked / pattern_candidate / unresolved | 이력·메시지 연결 여부, 단순 패턴 후보 여부 |
| 표현 | `representation`: original / preview / cover / metadata / fragment / unknown | 실제 확보한 데이터의 성격 |
| 복원 | `recovery_status`: complete / partial / metadata_only / missing / invalid | 로컬 바이트 확보·검증 결과 |
| 형식 | 원래 이름, 응답 MIME, 탐지 MIME, 검증 상태, 내보낸 상대 경로 | 파일명·선언 MIME·실제 형식의 불일치 보존 |
| 해시 | 원본 캐시 파일, 추출 본문, 조립 결과, 파생 미리보기의 해시 | 어느 바이트를 해시했는지 구분 |
| 시각 | 캐시 시각, 서비스 작업/메시지 시각과 각각의 출처 | 행위 시각과 캐시 관측 시각 혼동 방지 |
| 근거 위치 | `source_refs[]`, `evidence[]`, 규칙 버전, JSON pointer | 원본 파일·오프셋·엔트리·필드까지 추적 |
| 관계 | task/input/output/variant/preview 관계 | 작업 하나와 여러 파일, 파일 하나와 여러 캐시 엔트리 연결 |

`evidence_linked`는 이력에 연결됐다는 뜻이며 실제 사람이 수행한 행위를 독립적으로 확정한다는 뜻은 아니다. 메타데이터의 파일 크기·서비스 해시와 JSON 응답 자체의 크기·SHA-256은 다른 필드로 보존한다. 서비스 해시의 알고리즘도 확인 없이 SHA-256으로 취급하지 않는다.

중복 제거는 자산 ID·명시적 관계와 본문 해시를 함께 사용한다. 같은 내용이 서로 다른 작업의 입력/출력으로 사용된 관계는 없애지 않는다. 같은 원본의 썸네일·크기·포맷 변형은 별도 representation으로 보존한다.

## 5. 구현 순서와 검증 문턱

### 0단계 — PDF 사례와 실제 자료의 기준표 작성

- 업로드 5서비스, 생성 5서비스, 네트워크 5서비스를 검증 항목으로 만든다.
- 각 항목에 PDF 쪽수, 관측 방식(로컬/온라인), 기대 역할, 실제 원본 파일·엔트리·ID·해시, 확보 여부를 기록한다.
- 원본 캐시 본문 전체에서 URL·ID·MIME·형식을 확인한다. 현재 분류기의 결과에 없다는 이유만으로 증거가 없다고 판단하지 않는다.
- 현재 E01과 `01_Cache_Data`/`02_Cache_Data`의 범위를 구분한다. scenario1 E01 파일 자체를 확보했는지는 별도 확인한다.
- 원본이 없는 사례는 미검증으로 둔다. 스크린샷에서 임의의 바이너리를 만들어 복원 성공으로 처리하지 않는다.

완료: 15개 항목마다 검증 자료와 기대 결과 또는 자료 부족 사유가 정리됨.

### 1단계 — 계약·형식 검사·열람용 내보내기

- 새 계약과 관계 구조를 합의하고 버전·기존 소비자 호환 방식을 정한다.
- 후보 수집 → MIME/시그니처/디코더 검사 → 짧은 해시 이름+검증된 확장자로 내보내기 구현.
- PNG/JPEG/WebP는 실제 디코딩, 문서는 OLE/ZIP·OOXML/RTF 등 내부 구조로 검증한다. ZIP magic만으로 DOCX라 하지 않는다.
- 오디오·영상은 컨테이너 파싱과 필요한 디코드 검사를 분리한다. 도구 부재나 타임아웃은 미검증 상태로 보고한다.
- 원문 메타데이터는 파일명의 경로 구분자를 실행 경로로 쓰지 않으며, JSONL·SQLite에 데이터로 보존한다.

완료: 긴 URL로 실패하지 않고, 확인한 이미지는 직접 열리며, JSON 오류 응답과 형식 미확인 조각이 미디어 파일로 위장되지 않음.

### 2단계 — 서비스별 개체 추출·관계 연결

권장 순서: **DeeVid → ElevenLabs → Gemini → ChatGPT·Claude**. 현재 자료에서 재현 가능한 문제부터 처리한다.

- DeeVid: 각 creation의 입력 ID/이름/URL, 출력 URL, 커버, 작업 시각·상태를 보존한다. 파일명만 주어진 입력도 문맥에 맞게 연결하고 자산 하나를 첫 작업 한 건에만 묶지 않는다. 정확한 JSON 키 철자·별칭은 실자료로 확인한다. URL만 일치하면 후보로 남긴다.
- ElevenLabs: voice/sample/history/preview를 별도 개체로 추출하고 서로 연결한다. history 텍스트·시각·모델·보이스와 실제 오디오를 대조한다. `/samples/`, audio MIME, 보이스 기본/클론 여부 중 하나만으로 역할을 고정하지 않는다.
- Gemini: PDF 기준 이미지와 현 픽스처를 대조한 뒤 자산 ID·변형·본문 관계를 보강한다. 크기 순서나 워터마크 존재만으로 사용자 업로드/AI 생성 전체를 판정하지 않는다.
- ChatGPT: 사용자 첨부·assistant 출력의 파일 ID, asset pointer, 다운로드 메타데이터를 파일별로 연결한다. 재귀적으로 모은 이름 목록과 URL 목록을 위치만으로 짝짓지 않는다. 전달 endpoint와 접근 거부 JSON을 역할/복원 근거로 오인하지 않는다.
- Claude: 미리보기와 원본/출력 문서를 구분하고 `/api/.../files/...` 중간 ID의 의미를 확인한다. 현재 코드가 가정하는 conversation ID와 PDF 화면의 실제 경로가 맞는지 재검증한다.
- 모든 서비스: URL은 파싱한 host/path/query로 검사한다. 서비스 문자열이 다른 호스트의 경로나 query에 들어간 경우는 제외한다.

완료: 기준표의 연결된 파일·메타데이터가 개체 단위로 나오고, 관계 없는 CDN 이미지·커버·미리듣기·접근 거부가 확정 업로드/생성 파일로 섞이지 않음.

### 3단계 — Sparse/Range 영상 복원

- 현재 parser의 `cache_key`, 엔트리 주소, 필요한 stream 메타데이터와 원시 HTTP 헤더를 보존한다.
- 확인된 Chrome/Blockfile 버전에 맞는 Chromium sparse 구조를 확인하고 부모·자식 식별자, 블록 유효 범위, 논리 오프셋을 해석한다. 자식 번호만 보고 이어 붙이지 않는다.
- URL뿐 아니라 캐시 파티션·부모 식별자·버전 정보/validator 등으로 같은 리소스의 조각인지 판단한다.
- 중복, 순서 뒤바뀜, 빈 구간, 충돌 범위, 잘린 블록을 검출한다. 누락 영역을 임의의 바이트로 채워 완전 복원으로 표시하지 않는다.
- 논리 범위의 완전성과 컨테이너·재생 가능성을 각각 검사한다. 한쪽만 통과한 파일은 완전 복원으로 승격하지 않는다.
- 조립 결과마다 참여 엔트리·원본 범위·출력 범위·해시를 기록한다.

완료: 완전한 합성 샘플은 원본 해시·전체 디코드 일치, 누락/충돌 샘플은 partial/invalid. 실제 E01은 확보된 범위에 따라 성공 또는 부분 복원을 정직하게 보고함.

### 4단계 — 네트워크 상태 획득·분석

- E01의 프로필별 실제 `Network Persistent State` 위치를 확인하고 원본 이름·경로·해시를 유지하여 추가 획득한다.
- Cache_Data를 가진 프로필에만 탐색이 묶이지 않도록 프로필 발견 범위를 검토한다.
- servers, alternative_service, network_stats, anonymization, broken alternative service 구조를 파싱한다.
- host/port/protocol/상태와 원시 시간값·변환 시간값을 별도 필드로 보존한다. 원본 JSON pointer까지 연결한다.
- 네트워크 기록이 없으면 not_found/not_collected/parse_error를 구분한다. 일반적인 서버 상태 흔적을 파일 업로드나 생성 행위로 변환하지 않는다.

완료: PDF의 5개 서비스 네트워크 관측 형태를 표현하며, 만료 시각이 방문 시각으로 표시되지 않음.

### 5단계 — CLI·결과 저장·두 시나리오 재검증

- 기존 획득·캐시 파싱 후 개체 추출·복원·내보내기를 연결한다.
- E01을 매번 다시 해시하지 않고 기존 acquired manifest에서 재분석할 수 있는 명령을 추가한다. 입력 파일 해시를 재확인하고 기존 결과는 덮어쓰지 않는다.
- 서비스·역할·근거·복원 상태는 아티팩트 JSONL·SQLite에 저장한다. 전체 캐시 목록은 정규화 파일로 보존한다.
- 완전 파일·부분 파일·메타데이터만·후보·네트워크 상태의 건수를 각각 표시한다.
- scenario1과 DeepFake_DeepVoice를 별도 케이스로 검증하고, PDF의 기대 항목별 일치/불일치/자료 부족을 기록한다.

완료: 복원 파일과 JSONL·SQLite에서 근거 확인·원본 추적을 수행할 수 있으며, 저장 무결성과 분류 정확도·복원 완전성의 검증 결과가 분리됨.

## 6. 제안하는 결과 구조와 CLI

아래는 새 출력 제안이다. 현재 명령과 결과 파일명을 이미 바꿨다는 뜻이 아니다.

```text
<case>/
  run.json
  acquired/                 # 원본 캐시·추가 획득 파일과 매니페스트
  classified/               # 전체 캐시 엔트리·보존 본문
  normalized/               # 기존 호환 출력
  artifacts.jsonl           # 파일/메타데이터 개체별 최종 레코드
  artifacts.sqlite3         # artifacts, sources, relationships, network_records
  validation_summary.json   # 무결성·분류·복원·시나리오별 검증 결과
  files/<service>/<artifact_id>/<sha256>.<실제 확장자>
  previews/                 # 파생 미리보기, 원본과 구분
  partial/                  # 불완전 파일 및 범위 정보
```

```bash
# 제안: 기존 획득본으로 반복 개발·검증
gentrace analyze --cache <acquired.json> --out <new-case-dir>

# 제안: 전체 실행에 새 분석·복원 결과까지 포함
gentrace run --image <first.E01> --out <new-case-dir>
```

메타데이터 URL은 자동 열기/다운로드하지 않고 발견한 참조로 저장한다. 추후 온라인 수집을 도입한다면 별도 실행으로 수집 시각·HTTP 상태·원격 출처·다운로드 해시를 기록하고 E01 복원 결과와 구분한다.

## 8. 검증 항목

- 긴 URL, 유니코드 이름, 확장자 위장, 동일 이름의 다른 내용, 프로필 간 동일 본문.
- 파일 한 개의 여러 응답·변형, JSON 한 개의 여러 파일, 같은 자산이 여러 작업에서 사용된 경우.
- DeeVid 무관한 CDN 이미지, 커버, 입력 이미지, 영상 조각, URL만 발견된 출력.
- ElevenLabs 업로드 샘플·미리듣기·TTS 결과와 JSON만 존재하는 경우.
- ChatGPT user 첨부/assistant 출력이 같은 endpoint를 쓰는 경우와 접근 거부 응답.
- Claude 원본·preview 구분, `.doc`/`.docx`/octet-stream 실제 형식 검사.
- Gemini 같은 경로의 서로 다른 역할 및 같은 자산의 다른 포맷·크기 변형.
- Range 완전/누락/중복/충돌/다른 버전 혼합, 디코더 실패·시간 초과.
- 네트워크 만료·실패 시각과 행위 시각 분리, 같은 파티션을 세션으로 단정하지 않는지 확인.
- 익명화 합성 테스트 + 로컬 실자료 대조를 분리. ChromeCacheView/Hindsight와 엔트리·본문을 대조하고 불일치는 원시 바이트로 확인.
- 서비스별 수동 라벨이 검증된 집합에서 오탐·누락·미확정 수를 보고. 전체 캐시 건수나 기존 테스트 통과만으로 분류 정확도를 대체하지 않음.

우선 착수 단위는 **기준표 작성 → 이미지/문서 내보내기 → DeeVid·ElevenLabs의 근거와 복원 상태 분리**다. 영상 재조립은 별도 검증 단계로 진행하며, 아직 구현하지 않은 상태에서는 부분 데이터임을 명확히 표시한다.
